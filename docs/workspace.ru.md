# Рабочее пространство

[English](workspace.md) · **Русский**

verso находит корпус через один модуль, `verso.core.workspace`, и никогда не по тому, где лежит его
собственный код. Рабочее пространство — это каталог с файлом `verso.toml`; всё, что библиотека читает
о корпусе, — его села, его слой имён (поверх базового словаря, который поставляет библиотека,
`[names] base = "ru"`), его места и владельцы — названо в этом файле или лежит рядом с ним.

## Как его находят

В таком порядке:

1. самый внутренний `workspace.use(root)` (контекстный менеджер, для кода и тестов);
2. `VERSO_WORKSPACE` — путь к каталогу;
3. `verso.toml` в рабочем каталоге и выше — но не через границу git: каталог с `.git` и без
   `verso.toml` — это ошибка, так что вложенная копия репозитория никогда не читает данные внешней.

`verso <command> --workspace DIR` задаёт переменную для этой команды. Задавайте `VERSO_WORKSPACE` для
одной команды, а не через `export`: она сильнее рабочего каталога. `verso workspace root` и
`verso workspace villages` печатают то, что нашлось.

Ответ запоминается на процесс с первого вопроса. Импорт модуля никогда ничего не спрашивает: `--help`
и импорт откуда угодно работают без рабочего пространства. Каждому дочернему процессу Python, который
запускает verso, рабочее пространство передаётся в окружении.

## `verso.toml`

```toml
schema = 6
plugins = ["ru"]
villages = ["Степанчиково"]

[names]
layers = ["names"]       # слои имён корпуса поверх поставляемого базового; ниже

[corpus]
dir = "corpus"           # собственные данные корпуса, ниже

[notes]
globs = ["**/*.md"]      # заметки, которые читает `verso stale-notes`

[tools]
path = ["/opt/terraform/bin"]   # где ещё искать terraform и geni после PATH

[i18n]
locale = "en"            # язык интерфейса; см. руководство по языку
```

- `villages` — каталоги сёл корпуса, по названиям, по порядку.
- `plugins` — плагины, с которыми работает рабочее пространство (см. [плагины](plugins.ru.md)); файл
  схемы 1–3 читается как `["ru"]`, файл схемы 4 без этого ключа — это одно ядро.
- `[names]` — словарь имён: схема 6 складывает слои поверх базового словаря, который поставляет
  библиотека (см. [словарь имён](#словарь-имён)); файл схемы 5 или более старой называет свою старую
  таблицу ключом `dir`, а без `[names]` первый же поиск имени завершается ошибкой, а не отвечает
  «такого имени нет» из пустой таблицы.
- `[i18n]` — язык интерфейса (`locale`) и включённые языковые пакеты (`packs`), см.
  [язык интерфейса](i18n.ru.md); файл схемы 4 или более старой говорит по-русски, файл схемы 5 без этой
  таблицы — по-английски.
- `[translit]` (схема 7) — профиль транслитерации для каждой роли: `address` пишет res_names
  (адрес Terraform), `display` — имена, которые читает человек (латинские имена профиля Geni).
  Незаписанный ключ — это `ru-v2`; имя, которого нет ни в одном профиле, отвергается. Файл схемы 6 или
  более старой пишет обе роли по `ru-v1` и по `transliteration.toml` корпуса, как всегда. См.
  [правила транслитерации](#правила-транслитерации).
- `[app]` — собственные настройки страницы вычитки (`cache`, `photos_library`, `port`), которых
  библиотека никогда не читает.

Неизвестный ключ отвергается с названием файла и ключа; полный список — в
[справочнике](reference/workspace-keys.md).

## Словарь имён

Что такое имя — его основа, его формы, отчества, которые оно даёт, — определяется суммой слоёв имён,
снизу вверх: статья верхнего слоя целиком заменяет статью нижнего слоя с тем же ключом (пол и имя или
форма), и ничто не зависит от порядка строк. `[names]` схемы 6:

```toml
[names]
base = "ru"                       # базовый словарь, на котором стоят слои; false — без него (по умолчанию "ru")
layers = ["corpus/names"]         # каталоги над ним, снизу вверх (по умолчанию: нет)
writable = "corpus/names"         # слой, в который добавляют имя (по умолчанию: верхний слой)
```

- `base` — `"ru"` — это базовый словарь, который поставляет verso-ru (собран по алфавиту Требника
  1906 года, Викиданным и написаниям метрических книг, в каждой строке указан источник); любое другое
  значение отвергается при первом поиске, `false` складывает одни слои.
- `layers` — каждый слой это каталог из трёх файлов TSV, `names.tsv`, `forms.tsv` и
  `patronymics.tsv`, отсортированных по ключу; таблица, которой в каталоге нет, пуста, а каталог,
  которого нет, отвергается при первом поиске. Слой оставляет пустыми формы, которые дают правила
  (родительный падеж, отчество); ячейка форм `-` говорит, что у имени нет такой формы — правила её не
  заполняют, и обратный поиск (краткое отчество → его отец) её не находит. Строка names с `-` в
  `bases` говорит, что пары (пол, имя) не существует: она убирает статью этого ключа только у нижних
  слоёв, вместе с её формами, и имя отвечает так, будто ни один слой не держал его с этим полом
  (базовый словарь, под которым ничего нет, такую строку писать не может). Имя с источником `ignore`
  — это имя, которое словарь знает и сознательно оставляет в стороне. Каталог со старым `names.csv`
  вместо `names.tsv` читается как старая таблица, с `DeprecationWarning` — до 0.2.
- `writable` — один из `layers`; имя, которое не слой, отвергается.
- `dir` — ключ схемы 5, в схеме 6 он отвергается. Файл схемы 6 без `[names]` состоит из одного
  базового словаря.

Хост, который хранит имена не в файлах, а, скажем, в строках сервера, передаёт библиотеке слой как
источник на то время, пока она работает в рабочем пространстве: `verso.ru.naming.layers.provided(directory, source)`
делает `source` (`LayerSource`) слоем, который `[names] layers` называет по пути `directory`; такого
каталога тогда может и не быть. Источник, у которого есть `identity`, хранится между рабочими
пространствами так же, как каталог (`IdentifiedSource`); его `stamp()` должен меняться при каждой
записи, из любого процесса, а хост, записавший слой, вызывает `names_registry.invalidate(identity)`,
чтобы следующий поиск прочитал его сразу, не сбрасывая словари других слоёв.

Файл схемы 5 или более старой читается как всегда: его `[names] dir` — один слой, старые таблицы
скомпилированы, и **под ним нет базового словаря** — имя, которого старая таблица не знает, остаётся
неизвестным.

Загрузка словаря только читает слои и складывает их, больше ничего: обратный индекс (краткое или
современное отчество, родительный падеж) строится при первом обращении, и два имени, которым правила
дают один ключ, отвечают там в фиксированном порядке. Отвергает их проверка — `Lexicon.complete()`,
которую запускают сборка базового словаря, линтер слоёв (LEX007) и `verso names layer-diff`; а закрепление
(pin) в `patronymics.tsv` слоя решает, какое из имён остаётся.

### Добавление, удаление, проверка и объяснение имени

```
verso names add --gender Ж --name Евфрасиния --base Ефросиния --genitive Евфрасинии --source "МК 1917" [--dry-run]
verso names remove --gender Ж --name Евфрасиния [--dry-run]
verso names check [--layer DIR | --all]
verso names explain Евфрасиния [--gender Ж]
```

`add` пишет строку в записываемый слой — тот, что называет `[names] writable`; `--layer DIR` может
назвать только этот слой, слой, который не записываемый, отвергается (чтобы править его намеренно,
измените `[names]`): строку имени в `names.tsv` и, если дана форма, её строку в `forms.tsv`; два файла
пишутся вместе или не пишется ни один. У строки нет места и порядка, у ключа одна строка, а ключ,
который слой уже держит, отвергается. `--gender` — это `М` или `Ж`; формы — `--genitive`, `--patr-m`,
`--patr-f`, `--patr-old-m` и `--patr-old-f` (также `--patronymic-m` и так далее): пропущенная форма —
та, что дают правила, форма со значением `-` — «такой формы нет»; `--source` по умолчанию `editor`.
Новые строки сначала читает линтер слоёв поверх слоёв под ними: жёсткая находка — LEX001 (ключ, по
которому никакой поиск спросить не может), LEX003 (основа, которой не держит ни один слой), LEX007
(два вывода одного отчества) — отвергает их, код выхода 1 и ничего не записано; строка, на которую
сумма и так отвечает так же (LEX005), записывается, с предупреждением об этом. Если формы даны для
имени, которое слои уже держат, и нет `--base`, пишется только строка форм. `--origin` и
`--declension` — столбцы старого `names.csv`, здесь они отвергаются.

`add --replace` заменяет строку ключа, который записываемый слой уже держит, вместо того чтобы
отвергнуть его. В каждой таблице, которую пишет команда, — `names.tsv` и `forms.tsv`, если даны формы,
— строка этого ключа заменяется целиком; таблица, которую она не пишет, остаётся как есть, так что
`--replace --base X` без форм сохраняет старую строку `forms.tsv`. Новую строку читает линтер поверх
слоёв под ней, а не относительно строки, которую она заменяет (замена, после которой строка равна
базовой, — это LEX005), и для каждой команда печатает «replaced». Рабочее пространство схемы 5 или
более старой, где нет строк слоя для замены, отвергает её (код 1).

`remove` удаляет строки ключа в слое (его строки в `names.tsv` и `forms.tsv`). Имя, которое держит
только нижний слой — базовый словарь, — убирается из стопки строкой удаления (`-` в bases), записанной
в слой, а повторное удаление стирает эту строку. В обоих случаях команда говорит об этом, а также
когда ключ ещё держит слой ниже, когда другие имена ещё имеют удалённое своей основой (они отвечают
как написаны; LEX003 в `check`) и — предупреждением, не отказом — сколько записей сёл рабочего
пространства ещё пишут это имя (`written` как личное имя в `person(…)`; файлы читаются как синтаксис).
`--gender -` — это статья имени без пола. Код 1: ни один слой не держит ключ.

`check` читает записываемый слой линтером (LEX001–LEX007), либо слой, который называет `--layer`,
либо при `--all` каждый слой, включая базовый словарь, и их сумму. Каждая находка печатается как
`layer/file:line: message`; код 1, когда одна из находок жёсткая (совет, LEX004 и LEX005, проходит).

`explain` печатает для одного имени ответ `canonicalize_name`, `matching_base`,
`genitive_given_name`, `get_gender_from_name`, а также `derive_patronymic` и `derive_old_patronymic`
для сына и дочери, и под каждым — статьи, из которых он прочитан, каждую со своим слоем; функция,
читающая форму, показывает ячейку, которую читает, с пометкой слоя или `rule` (`verso.ru.naming.forms`),
если ни один слой её не пишет. Без `--gender` она спрашивает для каждого пола, в котором словарь держит это имя.

В рабочем пространстве схемы ≤ 5 `add` пишет свою строку в старый `names.csv`, как всегда (`--path` —
другой файл, об этом говорит заметка); `explain` читает старые таблицы как один слой; `remove` и
`check` предназначены для слоёв, код 1.

Имя, которое держит статья списка игнорируемых (источник `ignore`), не получает от правил никакой
формы: оно известно и не проверяется, и никакого отчества или родительного падежа для него не
выдаётся, пока строка форм не скажет его. Имя, единственной основы которого не держит ни один слой —
слой, написанный поверх базового словаря, который убрал более поздний релиз, — всё равно
загружается и отвечает как имя без основы (как написано); `check` говорит LEX003.

### От старой таблицы к слою

```
verso names layer-diff --from-legacy DIR --base ru --oracle FILE --out DIR
```

пишет наименьший слой поверх базового словаря, который отвечает на каждый вопрос оракула так же, как
старые таблицы `--from-legacy`. Оракул — это запись того, что корпус спрашивал у своих функций имён,
файл TSV по строке на вопрос:

```
function<TAB>args_json<TAB>answer_json
```

- строка, начинающаяся с `#`, — комментарий; строки отсортированы как строки;
- `function` — простое имя функции имён (`canonicalize_name`, `matching_base`,
  `derive_patronymic` …);
- `args_json` — JSON-список всех её параметров по порядку, с применёнными значениями по умолчанию;
  пол записывается как `"M"`, `"F"` или `null`;
- `answer_json` — ответ в той же нотации или `{"raises": "<the exception's class>"}`;
- JSON пишется компактно, ключи отсортированы, не-ASCII как есть.

Для каждого вопроса, на который базовый словарь отвечает иначе, берутся статьи старой таблицы тех
ключей, по которым вопрос искали, — имя с его формами, имена, чьи формы дают отчество, закрепление —
и это повторяется, пока все вопросы не сойдутся. Где подошли бы и имя, и закрепление, берётся имя
(оно отвечает и на другие вопросы об этом имени); вопрос, который эти ключи не решают, получает
ответ старой таблицы, записанный как закрепление, ячейка форм или `-`, если старая таблица не знает
формы, которую дали бы правила; а где базовый словарь держит имя с полом, с которым его не держит старая
таблица, и ничто другое не решает вопрос о нём, строка names с `-` в bases убирает эту пару (пол,
имя). Помимо вопросов оракула, она спрашивает женскую свёртку каждого отчества, которое называет
оракул (`feminine_patronymic`, форму, по которой проверка консолидации сравнивает два отчества).

Затем она отбрасывает то, на что базовый словарь отвечает так же. Каждая статья, которая может
отвечать так, как базовый словарь, — статья имени, которую он держит так же, статья форм, чьи формы
он даёт так же, любое закрепление, — отбрасывается сразу; для каждого вопроса, на который тогда
отвечают иначе, статьи, которые он читает, возвращаются на место. Статьи, возвращённые группой,
затем пробуются по одной: каждая, чьи собственные вопросы без неё всё ещё отвечают как по старой
таблице, уходит, а последний полный прогон возвращает то, что вопросу всё ещё нужно. Каждая статья
пишется с источником `legacy` — кроме имени из старого списка игнорируемых, которое сохраняет
источник `ignore`, отметку, по которой на него отвечают. Одни и те же входные данные дают одни и те
же байты.

Код 1 перечисляет вопросы, которых не решает ни одна статья, — слой всё равно записан. Другой код 1 —
два имени, чьи правила дают одно отчество, на что старые таблицы отвечают тем, что закрепление
записать не может: конфликт назван, и слой не записан. Третий — ответ, который нотация оракула
вместить не может.

## Правила транслитерации

verso-ru поставляет два профиля, каждый заморожен своим хешем: `ru-v1` — прежнее написание
res_names (`Jakov`, `Hohrjakov`) и `ru-v2` — BGN/PCGN без апострофов (`Yakov`, `Khokhryakov`, `Yury`,
`Darya`, `Maria`, `Semyon`). Слово, которое профиль должен написать целиком, — это **правило**, и со
схемы 7 правила — строки слоёв имён: четвёртый файл рядом с тремя файлами слоя, `translit.tsv`:

```
profile	word	latin	source	note
ru-v1	Чубарев	Tchoubarev	editor
ru-v2	Сорокоплехин	Sorokoplekhine	editor	as the family writes it
```

Правило привязано к своему профилю: правило `ru-v1` ничего не говорит о `ru-v2`. Слои складываются
так же, как имена: строка верхнего слоя заменяет строку нижнего с тем же ключом (профиль, слово),
`-` в `latin` убирает правило нижнего слоя, а правило добавляется в слой, который называет
`[names] writable`. Файл схемы 7, в корпусе которого всё ещё лежит `transliteration.toml`,
отвергается, пока его правила не перенесены в слой (`verso translit migrate`).

`verso translit show WORD` говорит, как каждая роль пишет слово и по какому правилу; `add WORD LATIN`
и `remove WORD` пишут записываемый слой (правило профиля для показа, если `--profile` не называет
другой), после того как строку прочитал линтер слоёв: LEX008 (правило без профиля, для слова, которое
не одно кириллическое слово, ни для чего) и LEX010 (латинское написание с символом вне латинских
букв, апострофа, пробела и дефиса; для `ru-v1` — совет) отвергают её, LEX009 говорит, что правило
лишнее. Правило профиля, который пишет **адреса**, отвергается, пока в сгенерированном дереве
рабочего пространства (`<village>/terraform/geni/*.tf`) есть метка ресурса со словом так, как
этот профиль пишет его сейчас: правило переименовало бы адрес Terraform. Отказ называет вместо него
профиль для показа. `verso translit check` проверяет линтером правила каждого слоя.


Село — это каталог файлов DSL по годам — `<village>/<YYYY>/<village>_<kind>_<YYYY>.py` — и его
настройки, `<village>/village.toml`, которые читаются из собственного каталога села:

- `[geni]` — проекты Geni, в которые входит каждый профиль, и `project_rules`: проект для профиля,
  чьё место (его название или его развёрнутая локация) содержит подстроку — это таблица ядра; каждая
  другая таблица принадлежит плагину (ниже, verso-ru), и таблица, которую не читает ни один
  включённый плагин, — неизвестный ключ;
- `[census]` — прежний порядок ревизских сказок и исключения из цепочки ревизий;
- `[timeline]` — эпохи села на его хронологии;
- `[sheets]` — таблица Google, из которой импортируются его записи;
- `[csv]` — файлы, которые не пишут CSV.

## Данные корпуса

То, что библиотека знает о корпусе, — это данные, которые читаются в момент вызова через рабочее
пространство, а не код и не при импорте. В каталоге `[corpus] dir`:

| Файл | Что | Кто читает |
|---|---|---|
| `places.toml` | таблица на место: `city`, `county`, `state`, `country` и атрибуты плагинов (`familio` у verso-ru — его поселение Familio); другое написание — таблица с одним `same_as` | `verso.core.places` → транслятор, ULC001, Familio, хронология |
| `estates.toml` | владельцы и приходы: псевдонимы, девичьи роды, сёла помещиков, государственные крестьяне | `verso.ru.corpus_data.estates` → estate-conflicts, RTV001/RTV002 |
| `timeline.toml` | события хронологии | `verso.ru.corpus_data.timeline_events` |
| `transliteration.toml` | фамилии корпуса, которые профиль res_name пишет целиком | `verso.ru.naming.transliteration` |
| `statuses.py` | статусы помещиков корпуса, как константы `Status` | DSL (`from corpus.statuses import …`); библиотека через `verso.ru.domain.statuses.catalog()` |
| `statuses.toml` | те же статусы как данные, вместо модуля: таблица на константу (`text` и `gender` — `male` или `female` — где он есть), в порядке каталога, и необязательные таблицы псевдонимов `child_estate_aliases` и `estate_aliases` | библиотека через `verso.ru.domain.statuses.catalog()`, не выполняя никакого Python |

Каталог корпуса — это пакет, потому что DSL импортирует его статусы; рабочее пространство, где
каталог корпуса называется иначе, импортирует их под этим именем. Файл корпуса, изменённый, пока
процесс работает, читается заново при следующем вопросе. Без `[corpus]` данных корпуса нет — ни мест,
ни владельцев, ни событий, — и это не ошибка.

Корпус держит свои статусы как `statuses.py` или как `statuses.toml`, но не оба сразу: рабочее
пространство с обоими отвергается. `verso statuses-toml` печатает TOML модуля или пишет его с
`--out FILE`; чтобы перевести корпус на форму данных, выполните
`verso statuses-toml --out <corpus dir>/statuses.toml`, а затем удалите `statuses.py` вручную
(рабочее пространство отвергается, пока стоят оба). DSL импортирует `<the corpus directory>.statuses`
только из модуля. Изменение `statuses.toml` читается заново при следующем вопросе.

В `transliteration.toml` одна таблица, `[names]`: фамилия, как её пишут книги, и её латинское
написание (`"Сорокоплехин" = "Sorokoplekhin"`). Профиль res_name (ru-v1) пишет имя, которого не
знает, буква за буквой; фамилия, перечисленная здесь, пишется целиком, как res_names корпуса
всегда её писали. Имя, которое собственная таблица профиля уже пишет, здесь отвергается, как и любой
другой ключ. Поэтому `cyrillic_to_latin` и `generate_res_name` читают рабочее пространство: вызванные
вне его, они выбрасывают `WorkspaceError`, а не пишут фамилию корпуса иначе, чем её пишет его дерево.
